## 第0步：勘察与专家人设

### 勘察

先只列清单不读内容：本地有哪些目录/多少文件/什么格式，飞书上有哪些文档和知识库空间。给用户一份范围确认，让他有机会说"这个目录跳过"或"先做这一批"。

**同时问清楚三件建库前必须知道的事**，问了能省掉大量返工：

1. 这个方向你们做到什么阶段了？（预研 / 样机 / 量产前 / 已量产——决定了理论层要挖多深、对标层要多细）
2. 建这个库主要为了产出什么？（日常问答 / 写汇报 / 冲论文 / 报专利——决定了各层的投入配比）
3. 有没有绝对不能外传的内容？（决定哪些资料只进项目层且要标密级）

### 写 PROFILE.md

这是每次对话都会加载的人设文件，篇幅控制在一屏内。它的作用是让弱模型每次都自带专业上下文，不用临时判断"我现在在聊什么领域"。

```markdown
# 专家助手人设

## 身份
你是四轮独立转向（4WIS）方向的专家助手，服务于 <部门/项目组> 的 <项目名> 项目。

## 项目一句话
<从 blocks/项目定位.md 的一句话版同步过来>

## 当前阶段
样机验证阶段，第二轮样车调试中。

## 知识边界
- 项目层（我们的事实）：见 _kb/project/，以此为唯一权威
- 理论层（公开原理）：见 _kb/theory/，可引用但需标注为公开知识
- 对标层（外部动向）：见 _kb/landscape/，需给可核查链接
- 三层之外的内容：明说这是推测，不要混进上面任何一层

## 常用术语
4WIS / 四轮独立转向 / 线控转向 SBW / 阿克曼 Ackermann / 质心侧偏角 / 横摆角速度 /
蟹行模式 / 原地转向 / 转角比例控制 / 冗余失效 FailSafe / ...

## 说话方式
- 结论先行，给数据必给出处
- 不确定就说不确定，不要用流畅的表述掩盖不确定
- 涉及三层来源混合时，明确标出哪句话来自哪层
```

## 第1步：项目层·资料索引

### 本地文件

逐份建卡，一次一份，写完立刻存盘再处理下一份。卡片模板：

```markdown
# <资料标题>
- 来源: 本地 | `<绝对路径>`
- 链接: [<文件名>](file:///<绝对路径>)
- 类型: 需求文档 / 设计方案 / 试验报告 / 会议纪要 / 数据表 / 图纸
- 权威层级: 高 / 中 / 低
- 日期: <文档自身日期>
- 密级: <公开 / 内部 / 机密>
- 解析质量: 完整 / 部分缺失 / 扫描件有风险

## 一句话摘要

## 检索关键词
<中文术语、英文原词、缩写、口语说法，宁多勿少——这是手工倒排索引，直接决定日后检索命中率>

## 核心内容提要
- <关键结论/数据/规定> [位置: <章节/页码>]

## 涉及的理论主题
<对应 theory/ 下的哪些主题，没有就写"待补"——第3步会据此反推理论层要建什么>

## 与其他资料的关系
<引用 / 被取代 / 冲突 / 补充>

## 可提取的决策点
<这份资料里体现了什么技术选择或方案取舍？第2步会用到>
```

最后两个字段是这套方法特有的，别省：「涉及的理论主题」让理论层的建设有的放矢，「可提取的决策点」是第2步决策记录的原料。

### 飞书文档

用 `lark-doc` / `lark-wiki` / `lark-drive` 等 skill 拉取，**拉取后落成本地快照**再建卡，理由是办公电脑可能离线、飞书内容会变，快照保证了知识库自洽可复现。

卡片头部改为：

```markdown
- 来源: 飞书 | <文档标题>
- 链接: <飞书 URL>
- 快照: `_kb/project/cards/_snapshots/<token>.md`
- 同步时间: <YYYY-MM-DD HH:MM>
```

飞书上的会议纪要和讨论串价值很高——决策的**理由**往往只存在于聊天和纪要里，正式文档只留结论。第2步要重点挖这部分。

### 汇总

所有卡片建完后生成 `project/INDEX.md`，一份资料一行：标题、来源、日期、一句话摘要、检索关键词、卡片路径。

## 第2步：项目层·进度与决策

这一步决定了助手是"读过你们的文档"还是"懂你们的项目"，是整个建库里性价比最高的一步。

### TIMELINE.md

```markdown
# 项目时间线

## 2025 Q4 · 方案预研
- 完成三种转向执行方案的对比选型 → [D-001]
- 输出：《4WIS 总体技术方案 v0.9》

## 2026 Q1 · 首轮样机
- 单轮转向模组台架验证通过，转角精度 ±0.3°（目标 ±0.5°）
- 遇到问题：低速大转角时电流冲击超预期 → [OPEN-002]

## 2026 Q2 · 整车集成
- 四轮协同控制器上车，实现蟹行/原地转向基本功能
- 未达标：高速工况横摆稳定性不足 → [OPEN-005]

## 当前（2026 Q3）
第二轮样车调试中，重点攻关高速稳定性
```

时间线要**带指标和未达标项**，不要写成流水账。汇报材料里"我们做到哪了"这一节直接取材于此。

### DECISIONS.md

只追加，不改写。每条一个决策：

```markdown
## D-001 转向执行机构方案选型
- 时间: 2025-11
- 结论: 采用「独立转向电机 + 谐波减速器」方案
- 理由:
  - 转角范围可达 ±90°，满足蟹行和原地转向需求
  - 相比轮毂集成方案，簧下质量增加可控
- 否决方案:
  - 轮毂电机集成转向：簧下质量过大，影响操稳；且散热空间不足
  - 液压转向：响应慢，不满足线控冗余要求
- 依据: [选型对比报告](file:///...) · [2025-11-08 技术评审纪要](<飞书链接>)
- 状态: 已定

## D-004 高速工况控制策略
- 时间: 2026-06
- 结论: 暂定「前后轮同相比例转向 + 横摆角速度反馈修正」
- 理由: 零质心侧偏角策略在样车上标定难度大，先用简化策略保交付节点
- 否决方案: 纯零质心侧偏角控制——理论最优但标定周期不可控
- 依据: [2026-06-12 周会纪要](<飞书链接>)
- 状态: **临时方案，待复核** —— 若 OPEN-005 解决则重新评估
```

这个格式的价值在于三处：写汇报时"为什么这么做"直接有料；写论文时**否决方案和取舍理由往往就是创新点的论证部分**；写专利时"相比现有技术的改进"需要的正是这段推理。

**注意**：决策理由常常散落在会议纪要、飞书聊天、甚至只在人脑子里。资料里挖不到的，直接列清单问用户——这一步值得占用用户时间。

### OPEN.md

```markdown
## OPEN-005 高速工况横摆稳定性不足
- 现象: 80km/h 以上变道，横摆角速度超调约 15%
- 影响: 阻塞高速场景验收
- 当前假设: 后轮转角响应滞后 / 控制参数未针对高速段标定
- 待决: 是否引入车速自适应的转角比例调度
- 相关: [D-004] · [试验报告2026-06](...)
- 负责人/时间: <>
```

`OPEN.md` 是"知道自己不知道"的实现，也是会议提纲的主要原料——会议就是用来推进这些条目的。

## 第3步：理论层

### 反推需要哪些理论

不要漫无目的地补理论。做法是**扫一遍第1步所有卡片的「涉及的理论主题」字段**，汇总出实际用得上的清单，再补充几个"虽然资料里没提但这个领域绕不开"的主题。写成 `theory/MAP.md`：

```markdown
# 4WIS 学科地图

## 车辆动力学
- 2自由度自行车模型、侧偏角与侧偏刚度 → theory/车辆动力学基础.md
- 横摆角速度增益、稳态转向特性（不足/过多转向）
- 用在哪：D-004 控制策略、OPEN-005 高速稳定性

## 转向几何学
- 阿克曼转向几何与阿克曼误差 → theory/转向几何.md
- 四轮转向的几何关系、瞬时转向中心
- 用在哪：整车转向半径计算、蟹行模式运动学

## 控制理论
- 前后轮转角比例控制、零质心侧偏角控制、横摆角速度跟踪 → theory/4WS控制策略.md
- 用在哪：D-004

## 电机与执行机构
- PMSM 位置伺服、谐波减速器背隙与刚度
- 用在哪：D-001、转角精度指标

## 功能安全
- 线控转向冗余架构、失效降级策略、ISO 26262 相关概念
- 用在哪：量产前必补，当前资料覆盖不足 ← 缺口
```

最后那种"缺口"标注很有用——它同时告诉你项目本身可能存在的短板。

### 每个主题一份文件

```markdown
# 阿克曼转向几何

## 核心概念
<用几段话讲清楚，面向"能看懂但不是这个细分方向专家"的读者>

## 关键关系
<公式、图示描述、典型数量级>

## 在 4WIS 中的特殊性
<两轮转向的经典理论到四轮独立转向时哪些前提变了>

## 常见误区
<这一节价值很高：容易被搞错的地方，写材料和答辩时能避坑>

## 来源
- [已查证] <标题> <URL> —— <访问日期>
- [仅模型知识] <内容概述> —— 未联网核实，引用前建议复核
```

**`[已查证]` 和 `[仅模型知识]` 的区分是这一层的关键。** 模型在冷门技术细节和具体数值上出错概率不低，标出来让人知道哪些能直接用、哪些要复核。写论文和专利时，`[仅模型知识]` 的内容一律不能直接引用。

`theory/SOURCES.md` 汇总所有来源并标注可信度（标准/教科书 > 综述论文 > 厂商白皮书 > 技术博客）。

## 第4步：对标层

### COMPETITORS.md
谁在做、什么方案路线、公开的指标、量产状态、信息来源链接。重点记**方案路线差异**而不是营销话术——差异点才是你们汇报里"差异化优势"的对照基准。

### PAPERS.md
关键文献清单：标题、作者/机构、年份、核心贡献一句话、与本项目的关联、链接。按主题分组，别按时间堆。

### PRIOR_ART.md
专利现有技术，规矩最严：

```markdown
## PA-003 <专利名称>
- 公开号: <CNxxxxxxx>
- 申请人: <>
- 链接: <可点击的公开数据库链接>
- 技术方案要点: <>
- 与我方方案的关系: 相似点 / **区别点**
- 风险等级: 高（可能构成障碍）/ 中 / 低（仅背景技术）
```

**没有可核查链接的条目不要写进这个文件。** 专利撰写里现有技术检索的完整性直接影响授权前景和无效风险，宁可标注"检索不充分，需专业检索机构补充"，也不要用记忆凑数。

## 第5步：素材块

综合前四层，把反复要用的论述预先写好。每块提供三种长度，写完**交用户逐块审定**——这些文字之后会出现在所有对外材料里，值得花时间定稿。

```markdown
# 项目定位

## 一句话（用于 PPT 封面、邮件开头、电梯汇报）
面向 <应用场景> 的四轮独立转向系统，实现蟹行、原地转向与高机动性转向，
当前处于样机验证阶段。

## 一段（用于汇报开头、方案书概述）
<3-5 句：解决什么问题、技术路线、当前进展、目标>

## 一页（用于论文引言、立项书、详细方案背景）
<完整展开：行业背景 → 现有方案局限 → 我们的技术路线 → 预期价值 → 当前进展>
```

建议的素材块清单：项目定位、技术路线、关键指标（现状/目标/对标三栏）、核心难点、差异化优势、里程碑进度、风险与待决。

每块底部记录取材出处，交付时需要溯源就能查回去：

```markdown
---
取材: [D-001] [D-004] [总体技术方案v0.9](file:///...) [landscape/COMPETITORS.md]
定稿日期: 2026-07-21
```

## 增量同步

`_state.json` 记录每个来源的路径/URL、大小或版本、修改时间、建卡时间、是否人工修正过。重跑时只处理变动项。

飞书文档比本地文件变得勤，建议**每次生产重要交付物之前先跑一次项目层同步**，避免汇报里用了过期数据。

理论层和对标层不用频繁同步——它们的价值就在于稳定。

## 常见翻车场景

**跳过第2步直接建索引。** 最常见也最可惜。结果是助手能回答"文档里写了什么"，但答不了"我们为什么这么做"——而后者才是汇报、论文、专利的核心内容。

**理论层建成百科全书。** 不受控地补理论，建出一堆项目里根本用不上的内容。始终从卡片的「涉及的理论主题」反推，用不上的不建。

**素材块没让用户审定就投入使用。** 素材块的全部价值在于"经人确认过"，自动生成、直接使用的素材块只是把随机性提前了，没有消除。

**决策记录被改写。** 方案变更时直接改旧条目，导致历史丢失。永远新增+标注取代关系。当初为什么选错，在复盘和专利答复审查意见时都是关键信息。

**三层内容在卡片阶段就混了。** 比如在项目层卡片里顺手写了一段公开理论解释。之后所有交付物都会继承这个污染，且极难排查。三层各自的文件目录是物理隔离的，写之前先确认写在哪一层。
