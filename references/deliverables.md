## 通用第一步：定规格

动手之前把这几项问清楚，别猜。同一份项目内容，规格不同产出的材料可以完全不一样：

| 项 | 为什么必须问 |
|---|---|
| 读者是谁 | 决定技术深度、术语密度、说不说钱和资源 |
| 场合与时长 | 15分钟周会汇报 vs 1小时技术评审，信息量差 5 倍 |
| 目的 | 要资源 / 报进展 / 求决策 / 说服客户 —— 决定结构主线 |
| 篇幅 | 页数或字数 |
| 密级 | **对外材料必须按卡片的密级字段过滤，这一项漏了是事故** |

用户没说清的，宁可问一句。规格错了，后面写得再好都要返工。

## 通用必检：三层来源分离

所有交付物交付前都要过这一关：**随机抽三处事实性表述，回答它属于项目层、理论层还是对标层，以及读者能否分辨。**

分辨手段因交付物而异：

- 论文：靠标准引用格式，项目层内容即"本文工作"
- 专利：靠"背景技术"和"技术方案"两节的物理分隔
- PPT：靠页脚标注来源，或用不同的视觉标记
- 汇报：靠段落分区，或在句中明说"行业通行做法是…，我们的方案是…"

抽查发现分不清的，改到能分清为止。这一条不是格式洁癖——它防的是把公开知识当自研成果、把外部数据当自测数据这类会出事的错误。

## 汇报材料与 PPT

### 配方

| 读者 | 项目层 | 理论层 | 对标层 | 主线 |
|---|---|---|---|---|
| 管理层 | 70% | 5% | 25% | 进展 → 问题 → 要什么 |
| 技术评审 | 60% | 20% | 20% | 方案 → 依据 → 数据 → 待决 |
| 客户/外部 | 40%（过滤后） | 10% | 50% | 痛点 → 方案 → 差异化 → 案例 |
| 新人培训 | 40% | 50% | 10% | 原理 → 我们怎么做 → 现状 |

### 取材路径

- 项目背景 → `blocks/项目定位.md`
- 技术路线 → `blocks/技术路线.md` + `DECISIONS.md` 里的关键决策
- 进展 → `TIMELINE.md`（带指标，不要写成流水账）
- 数据 → 项目层卡片，**每个数字标出处**
- 定位/对比 → `blocks/差异化优势.md` + `landscape/COMPETITORS.md`
- 问题与风险 → `OPEN.md` + `blocks/风险与待决.md`

### 结构模板（技术评审场景）

```
1. 一页纸结论        ← blocks/项目定位.md 一段版 + 三条关键结论
2. 项目背景与目标     ← blocks/项目定位.md
3. 技术路线与关键决策  ← blocks/技术路线.md + DECISIONS.md
   （这里要讲"为什么这么选"，否决方案也要提——评审最想听的就是取舍）
4. 当前进展与指标     ← TIMELINE.md，指标用「现状 / 目标 / 对标」三栏
5. 关键问题与对策     ← OPEN.md
6. 下一步与所需支持   ← 明确到人、时间、资源
```

### PPT 特有注意

- **一页一个观点**，页标题直接写结论（"高速稳定性是当前主要瓶颈"，而不是"高速工况测试情况"）
- 数据页必须有出处，放页脚小字即可
- 指标一律用「现状 / 目标 / 对标」三栏对比，单看现状没有信息量
- 技术方案页优先画结构或流程，其次才是文字
- 备注页写口播要点——正式场合很有用，也是弱模型容易忘做的一项

### 检查清单

- [ ] 每个数字都能追回到项目层出处
- [ ] 理论解释没有被写成"我们发现/我们提出"
- [ ] 对标数据标了来源和采集时间（竞品指标会过期）
- [ ] 对外材料已按密级过滤
- [ ] 有明确的"要什么"（管理层汇报最容易漏这条）

## 会议提纲

会议提纲的价值不在于罗列议题，而在于**让每一项都有推进它所需的信息和明确的决策点**。写成流水账的提纲等于没写。

### 取材

主要来自 `OPEN.md`——会议本来就是用来推进待决事项的。其次是 `DECISIONS.md` 里标注"临时方案，待复核"的条目。

### 模板

```markdown
# <会议主题>
时间 / 参会人 / 预计时长

## 会议目标
<本次会议结束时要产出什么——决策？方案？分工？写不出来说明这个会可能不必开>

## 议题一：<高速工况横摆稳定性攻关>（20 min）
- 背景: <三句话说清来龙去脉> [OPEN-005]
- 现状数据: 80km/h 变道横摆角速度超调 15% [来源: 试验报告2026-06]
- 已尝试: <做过什么，结果如何>
- **待决问题**: 是否引入车速自适应转角比例调度？
- 决策所需: <还缺什么信息才能拍板>
- 需谁拍板: <角色>
- 备选方案: A) ... B) ... 各自代价

## 议题二：...

## 需同步事项（不讨论，5 min 过）
- <进展周知类内容放这里，别占讨论时间>

## 预留决议记录
| 议题 | 结论 | 责任人 | 时限 |
|---|---|---|---|
```

### 检查清单

- [ ] 每个议题都有明确的"待决问题"，而不只是"讨论一下 XX"
- [ ] 标出了每个决策需要谁拍板
- [ ] 区分了"要讨论的"和"只需周知的"
- [ ] 会后决议表已预留 —— 会议记录直接续写，并回填到 `DECISIONS.md`

**会后闭环**：会议产生的决策要新增进 `DECISIONS.md`，被解决的条目在 `OPEN.md` 里标关闭。这是知识库保持鲜活的主要途径，别漏。

## 论文

### 三层如何映射到论文结构

| 章节 | 主要来源 | 说明 |
|---|---|---|
| Introduction | 理论层 + 对标层 + 项目层 | 领域背景 → 现有方案局限 → 本文贡献声明 |
| Related Work | 对标层（`PAPERS.md`） | 按技术路线分组综述，不要按时间堆 |
| Method | 项目层 + 理论层 | 我们的方案；理论层提供公式化表达和记号 |
| Experiments | 项目层 | 试验数据，需可复现的描述 |
| Conclusion | 项目层 | 贡献回扣 + 局限 + 展望 |

### 贡献声明的写法

这是论文最容易出问题的地方，也是 `DECISIONS.md` 价值最大的地方。**贡献不是"我们做了一个四轮独立转向系统"，而是"我们在 X 约束下提出了 Y 做法，相比 Z 获得了 W 改进"。** 这个句式里的每个位置都有出处：

- X 约束 ← `DECISIONS.md` 决策背景
- Y 做法 ← 项目层技术方案
- Z 对照 ← `landscape/` 对标基准
- W 改进 ← 项目层试验数据

`DECISIONS.md` 里的**否决方案与理由**通常直接构成论文里"为什么不用更常见的做法"这一段论证——审稿人一定会问这个。

### 检查清单

- [ ] 贡献声明具体到可验证，不是泛泛的"设计并实现了"
- [ ] Related Work 覆盖了 `PAPERS.md` 里所有高相关文献
- [ ] 理论层里标 `[仅模型知识]` 的内容**一律不得直接引用**，必须查证到真实文献
- [ ] 每个实验数字对得上项目层原始记录
- [ ] 局限性诚实交代（`OPEN.md` 里的内容部分可转化）
- [ ] **发表前确认专利申请状态**（见下文）

## 专利交底书

专利是所有交付物里来源分层最要命的一类——**把公知技术写进"技术方案"当作自己的发明，轻则被驳回，重则埋下无效隐患。**

### 结构

```markdown
## 一、技术领域

## 二、背景技术
<严格来自 landscape/PRIOR_ART.md。客观描述现有技术方案及其缺陷，
 每条最好能对应到具体公开文献或专利公开号>

## 三、要解决的技术问题
<从背景技术的缺陷自然推导出来，不要跳跃>

## 四、技术方案
<严格来自项目层。这是发明的核心，要写清楚：
 - 整体架构
 - 关键部件/步骤及其连接或时序关系
 - 关键参数范围（注意上位与下位的平衡）
 - 至少一个完整的实施例>

## 五、有益效果
<项目层的试验数据 vs 背景技术的基准，要有可量化对比>

## 六、附图说明
```

### 特有风险与对策

**风险一：技术方案里混入公知技术。** 写完后逐条自查"这一条是我们想出来的，还是行业里本来就这么做的"。行业通行做法应当出现在"背景技术"里作为铺垫，而不是"技术方案"里作为发明点。

**风险二：现有技术检索不充分。** `PRIOR_ART.md` 里没有可核查链接的条目不能用。而且要诚实告诉用户：**agent 的检索不能替代专业检索**，交底书写完仍需专利代理人或检索机构做正式 FTO/新颖性检索。

**风险三：保护范围失衡。** 写得太上位容易被现有技术打掉，太下位则容易被绕开。交底书阶段的做法是：核心方案写上位，同时把已验证的具体参数和实施细节都列出来作为从属权利要求的素材，由代理人拿捏层级。

**风险四：有益效果空泛。** "提高了转向精度"没有意义，要写"转角控制精度由 ±0.5° 提升至 ±0.3°，在 XX 工况下测得"，并对应项目层数据出处。

### 检查清单

- [ ] "背景技术"里的每条都有公开来源，且不含任何我方未公开信息
- [ ] "技术方案"里的每条都确认是我方独创，不是行业通行做法
- [ ] 有益效果有量化数据且对应得上项目层记录
- [ ] 至少一个完整可实施的实施例
- [ ] 已提示用户"需专业检索机构补充正式检索"
- [ ] 已确认相关内容的公开状态（见下）

## 论文与专利的顺序问题

这一条独立成节，因为它是这个组合里最容易造成不可挽回损失的坑：

**论文发表、公开演讲、展会展示、甚至公开的技术博客，都可能构成"现有技术公开"，从而破坏自己后续专利申请的新颖性。**

所以当用户同时提到论文和专利时，**主动提醒确认这两件事的时间顺序和公开状态**：

- 相关技术方案是否已经申请专利？申请日是什么时候？
- 论文/材料计划何时公开？是否早于专利申请日？
- 对外汇报材料、客户方案书是否已经披露了准备申请专利的技术细节？

标准做法是**先申请专利、再发表论文**。这件事 agent 提醒一句成本极低，但用户真踩了代价极高——属于典型的"知道就能避免"的风险，值得每次涉及时都提一嘴。

同理，`blocks/` 里的素材块如果包含未申请专利的技术细节，在用于对外材料前应当过一遍这个问题。
