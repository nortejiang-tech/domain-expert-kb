# 移植与强弱模型分工

## 核心思路：按"保密性"和"算力需求"切分工作

这套方法能在弱模型上跑出同等水平，靠的不是提示词技巧，而是**把工作分配到合适的环境去做**。恰好有个漂亮的巧合：

**最吃模型能力的两层（理论层、对标层）恰好完全不含机密内容。**

所以可以这么分：

| 步骤 | 在哪做 | 为什么 |
|---|---|---|
| 0. 勘察与人设 | 任意 | 轻量 |
| 1. 项目层·资料索引 | **公司环境** | 资料和飞书权限都在这儿，且含机密 |
| 2. 项目层·进度与决策 | **公司环境** | 同上，且需要你本人参与访谈补充 |
| 3. 理论层 | **强模型 + 联网环境** | 最吃能力，但**全是公开知识，不涉密** |
| 4. 对标层 | **强模型 + 联网环境** | 需要联网检索，同样不涉密 |
| 5. 素材块 | 公司环境，你逐块审定 | 综合各层，但关键是人把关 |
| 交付物生产 | 公司环境 | 日常高频使用 |

第 3、4 步在外部环境（比如你自己的电脑 + 强模型 + 联网）做好之后，**产出就是一堆纯 markdown 文件**，拷进公司环境的 `_kb/theory/` 和 `_kb/landscape/` 即可。这两层本来就设计成"建好就冻结"，不需要频繁更新。

于是公司电脑上的弱模型，日常面对的是一个**已经被强模型充实过的知识库**，它的任务降级成检索、组装、填模板——这正是弱模型能做好的部分。

拷贝前留意一件事：外部环境建理论层时，**不要把项目层的机密细节当作检索关键词发到公网上**。用通用技术术语检索就够了（搜"四轮独立转向 横摆稳定性控制"，而不是你们的内部方案代号和具体参数）。

**`PROFILE.md` 建议直接并入 `.clinerules` / `QWEN.md`**，让专家人设每次对话都在场——这对弱模型的效果比任何提示技巧都明显。

## 针对弱模型的三处调整

### 一、分步驱动，不要长流程连跑

弱模型跑到长流程中段容易偏航。把建库拆成显式命令，每步产出文件后停下：

```
建库第0步            → 勘察 + 写 PROFILE.md，停
建库第1步 <目录名>    → 只处理这批资料的卡片，一次一份，写完即存
建库第2步            → 抽取 TIMELINE / DECISIONS / OPEN，列出需要我补充的问题
建库第5步            → 起草素材块，逐块交我审定
同步                 → 只处理变动的资料
```

Cline 支持 `.clinerules/workflows/` 下放工作流文件用 `/名称` 调用，正好适合这种分步设计。

每步从盘上读、往盘上写，某一步出错只损失那一步。

### 二、关键节点先复述再执行

```
执行建库第1步前，先复述：本批哪些文件、卡片模板有哪几个字段、产出到哪个目录。
复述完再开始，一次只处理一份文档。
```

成本极低，但对 10B 激活参数量级的模型，跳步率下降明显。

### 三、交付物先出大纲，确认后再展开

不要让弱模型一口气写完整份汇报。先出结构大纲和每节的取材来源，你看过点头，再逐节展开。

理由和分步建库一样：把一个大的开放任务，拆成若干个小的封闭任务。

## 精简版（贴进 .clinerules / QWEN.md）

```markdown
# <项目名> 专家助手

## 人设
你是 <技术方向> 的专家助手，服务于 <项目>。当前阶段：<>。
结论先行；给数据必给出处；不确定就说不确定。

## 知识库：_kb/  三层严格分离，不得混淆
- project/  我们的事实（INDEX / TIMELINE / DECISIONS / OPEN / cards）——唯一权威，引用需内部出处
- theory/   公开原理——可引用，须标注为公开知识；标 [仅模型知识] 的需复核后才能用于论文专利
- landscape/ 外部对标（COMPETITORS / PAPERS / PRIOR_ART）——须给可核查链接
- blocks/   已定稿素材块，三种长度：一句话 / 一段 / 一页
- PROFILE.md 本人设

## 回答问题时
1. 从 project/INDEX.md 和 blocks/ 定位，再读卡片，最后才翻原文对应章节
2. 答案里三层来源分开标注：文档依据（带出处）/ 公开原理（标注非我方资料）/ 外部对标（带链接）
3. 文档没覆盖的，在"边界与存疑"里说清楚，不要硬答

## 写交付物时
先问清规格：读者、场合时长、目的、篇幅、密级（对外材料必须按密级过滤）。
先出大纲和取材来源，我确认后再展开。
优先从 blocks/ 取现成素材，不要重新创作项目定位这类核心表述。

配方：
- 汇报/PPT：项目层为主 + 对标层定位。每个数字标出处；指标用"现状/目标/对标"三栏；
  页标题写结论不写话题；管理层汇报必须有明确的"要什么"
- 会议提纲：主要取自 OPEN.md。每个议题要有明确"待决问题"和"需谁拍板"，
  不能只写"讨论一下 XX"。会后决议回填 DECISIONS.md
- 论文：理论层做背景 + 对标层做 related work + 项目层做贡献。
  贡献声明句式："在 X 约束下提出 Y，相比 Z 获得 W 改进"。
  DECISIONS.md 里的否决方案理由用于论证"为什么不用常见做法"
- 专利交底：背景技术严格取自 PRIOR_ART.md（须有链接），技术方案严格取自项目层。
  写完逐条自查"这条是我们独创还是行业通行做法"——通行做法应放背景技术而非技术方案。
  有益效果要量化并对应项目层数据。提醒用户需专业机构补正式检索

## 底线
1. 三层来源任何时候不得混淆，读者必须能分辨哪句话属于哪层
2. 每条事实性结论必须有可核对的出处
3. 涉及论文与专利同时进行时，提醒确认"先申请专利再发表"，
   论文/公开材料可能破坏专利新颖性
```

## 效果不理想时优先查这两处

**检索关键词填得太窄。** 弱模型建卡时倾向于只填标题里已有的词，导致日后检索召回率低。发现问题时，可以把已有卡片导出，在强模型环境批量补充关键词字段再拷回——这是纯文本操作，很容易做。

**「边界与存疑」流于形式。** 弱模型爱写"无"。在规则里加一句"这一节写「无」需要给出理由"，逼它真的想一遍。

这两处也再次说明这套方法的设计意图：**质量可以用更强的模型或更多时间在建库阶段堆进去，堆进去的东西固化成文件，让之后每一次弱模型的使用都受益。**
